# OTPPhone — Architecture

End-to-end encrypted Android messenger with an optional **one-time-pad (stream-cipher) layer**
whose key material is exchanged **in person over Bluetooth**, never over the internet.

> **Honesty note up front:** the pad is generated by a CSPRNG (`SecureRandom`), so this is a
> *computationally* secure stream cipher, **not** an information-theoretic one-time pad. See
> [§9 Security properties & limitations](#9-security-properties--limitations). The "OTP"
> naming is kept for continuity; the security claims below are the accurate ones.

---

## 1. Components

```
┌─────────────────────────┐     wss (TLS)      ┌────────────────────────┐
│   Android app (Kotlin)  │ ◄────────────────► │  Relay server (Ktor)   │
│  Jetpack Compose UI     │   HPKE ciphertext  │  in-memory forwarder   │
│  Hilt DI                │   only             │  hosted on Fly.io      │
└───────────┬─────────────┘                    └────────────────────────┘
            │  Bluetooth (Nearby Connections), in person
            ▼
┌─────────────────────────┐
│  Peer's Android phone   │   ← OTP pad copied here once, locally
└─────────────────────────┘
```

| Component | Tech | Role |
|-----------|------|------|
| App | Kotlin, Compose, Hilt, Room, Tink, Nearby Connections, OkHttp, SQLCipher | All crypto + UI; holds private keys and pad material |
| Relay | Kotlin, Ktor (Netty) WebSocket, Tink | Blind forwarder of HPKE ciphertext; sees metadata only |
| Download page | Cloudflare Worker + R2 | Distributes the APK (`download.rhydianwilliams.com`) |

Two encryption layers protect every message:

1. **Transport (always on):** HPKE — DHKEM-X25519-HKDF-SHA256 + AES-256-GCM (Tink). Encrypted to
   the recipient's device public key, so the relay can never read content.
2. **OTP/stream-cipher (when a pad exists):** the plaintext is XOR'd with a unique slice of the
   shared pad *before* the HPKE layer. This is the part that requires the in-person Bluetooth exchange.

## 2. Identity

A device has **two** keypairs — an X25519 HPKE keypair (confidentiality) and an Ed25519 signing
keypair (authenticity) — and its `userId` is **derived from both public keys**, not random:

```
userId = base64url( SHA-256( HPKE public keyset ‖ Ed25519 signing public keyset ) )[:32]
```

This single fingerprint is used everywhere — message routing, conversation keys, OTP session keys,
**relay authentication**, **peer-key pinning**, and **message-signature verification** — and gives
these properties for free:

- A `userId` **cannot be claimed without the matching private keys** (basis of relay auth, §6).
- Both of a peer's public keys are **self-authenticating**: substituting either one produces a
  different fingerprint, so it can never match the expected `userId` → key-substitution MITM is
  blocked, and the signing key used to verify a peer's messages is provably the one bound to them.
- Every content frame is **signed** with the sender's Ed25519 key, so a message (or edit/unsend/
  reaction/…) can only be produced by the holder of `senderId`'s key — the relay merely forwards
  and **cannot forge or tamper** (see §4, §6).
- Rotating either device key changes the `userId` (so it's effectively a new contact).

Both keypairs are Tink keysets stored in Keystore-wrapped `EncryptedSharedPreferences`
(`DeviceKeyManager`). `UserIdentity` derives the fingerprint from them.

### 2.1 Connecting & exchanging HPKE keys (over the relay)

To message a peer you need their HPKE **public** key. These are distributed through the relay
(there is no central key directory):

- The app **connects to the relay as soon as it is open** — from the conversation list
  (`ConversationsViewModel`), not only inside a chat — so it can receive keys/messages anytime.
- On connect, and **immediately when you add a contact** (`announceKeyTo`), the app sends a
  `KEY_HELLO` (its public key) to that peer.
- A peer receiving a `KEY_HELLO` **pins** both keys (stored only if `fingerprint(hpke ‖ sig) ==
  senderId` *and* the frame's Ed25519 signature verifies) and
  replies **once** with a `key_ack` carrying its own keys. The ack does *not* trigger another reply —
  this avoids an infinite key↔key ping-pong that would otherwise flood the relay's rate limiter.
- An inbound key/message from someone you haven't added **auto-creates the conversation**
  (`ensureConversation`), so **one person adding the other is enough** — the other side's chat
  appears on its own.
- Until the peer's key is held, the chat shows **"Exchanging keys…"**; once received it becomes
  **HPKE** (or **OTP+HPKE** if a pad exists). Sending to a peer who has never been online is gated
  until that exchange can complete.

### 2.2 Sharing & verifying contacts

- **My ID** shows your `userId`, a **QR code** of it, and your **safety words**.
- **Add Contact** accepts a pasted ID or a **QR scan** (camera, `zxing-android-embedded`), and shows
  the contact's safety words for comparison.
- **Safety words** (`SafetyPhrase`) are a 4-word phrase derived from a `userId`
  (`SHA-256(userId)` → 4 words from a fixed 256-word list). It's a friendly, Signal-style
  verification aid you read aloud to confirm you added the right person. **Display-only** — the full
  ID/QR plus key-pinning remain authoritative; ~32 bits catches human error, not a determined attacker.
- The chat **⋮ menu** offers **Verify safety words** (re-check a contact at any time) and
  **Rename contact** (a local display name; names are per-device).

## 3. OTP pad: generation, storage, lifecycle  ⭐

This is the security-critical store, so it's described in full.

### 3.1 Generation

- The **advertiser** generates a pad with `SecureRandom` (default **1 MB**, `OTPGenerator.generateAndSealPad`).
- The identical bytes are transferred to the peer over Bluetooth (§5) and the **receiver re-seals
  the same bytes locally** — both sides end up with the same pad, each sealed under *its own*
  device key.

### 3.2 Where and how it is stored (defence in depth)

The pad is protected by **three** independent layers at rest:

```
 pad bytes (1 MB)
   └─ split into 4 KB chunks
        └─ each chunk sealed: AES-256-GCM under a per-session Android Keystore key   ① TEE/StrongBox
             └─ concatenated "sealed blob" stored Base64 in Room table `sealed_pads`
                  └─ entire Room DB encrypted at rest by SQLCipher (AES-256)          ② SQLCipher
                       └─ DB file in internal storage, allowBackup=false               ③ OS sandbox
```

**① Per-session Keystore key (the important one).**
Each session has an AES-256-GCM key in the **Android Keystore** under alias `otp_pad_<sessionId>`,
**StrongBox-backed where available, TEE otherwise** (`OTPGenerator.provisionKeyIfAbsent` tries
StrongBox then falls back). This key is **non-exportable** — even root cannot read it; it can only
be *used* on-device. The sealed pad blob is therefore useless if copied off the device.

**Chunked sealing (`OTPGenerator`).** The blob is a concatenation of independently-sealed 4 KB
chunks, each `[12-byte IV][ciphertext + 16-byte GCM tag]` (segment size 4124 B). This is what lets a
single short message decrypt only the **one chunk** it needs (~4 KB through the TEE) instead of the
whole 1 MB — and lets erase-after-use (§3.5) re-seal just that chunk.

**② SQLCipher.** The blob lives in the `sealed_pads` table of a Room database opened through
SQLCipher's `SupportFactory`, so the whole DB file is AES-256 encrypted on disk
(`AppDatabase`, `OTPVaultManager`).

**③ OS sandbox.** The DB (`otpphone.db`) is in app-private internal storage; `allowBackup=false`,
`fullBackupContent=false`, and the data-extraction rules exclude everything, so it never leaves the
device via cloud backup or device-transfer.

The **SQLCipher passphrase** itself is a 32-byte random value sealed under a *separate* Keystore
AES-GCM key, with only the sealed blob kept in private `SharedPreferences`
(`DatabasePassphraseManager`). It's re-derived from the Keystore on each launch.

### 3.3 Schema (Room v3, SQLCipher-encrypted)

| Table | Key columns | Notes |
|-------|-------------|-------|
| `otp_sessions` | `sessionId`, `peerId`, `totalPadBytes`, **`consumedBytes`**, `keystoreAlias`, `isActive` | Offset bookkeeping per session |
| `sealed_pads` | `sessionId`, `keystoreAlias`, `sealedBlobBase64` (chunked), `totalBytes` | The sealed pad blob |
| `messages` | `plaintextBody`, `ciphertextBase64`, `encryptionMode`, `otpSessionId`, `otpByteOffset`, `isOwn` | Plaintext is SQLCipher-encrypted at rest; **purged on Destroy Vault** |
| `pending_messages` | `wireMessageJson` | Offline send queue (already-encrypted frames) |

### 3.4 No keystream is ever reused (the cardinal rule)

Because **both endpoints hold the same pad**, the pad is **split by direction** so the two sides can
never XOR with the same bytes (`OTPVaultManager.txRegionFor`/`rxRegionFor`):

```
lower userId  transmits from [0, N/2)          ← determined by canonical userId comparison
higher userId transmits from [N/2, N)
```

One side's transmit region is exactly the other's receive region, and they never overlap. On the
receive path, an inbound offset outside the peer's region is **rejected** as reuse/tampering
(`assertInboundOffset`). Within a device, `consumedBytes` is advanced **atomically under a mutex and
persisted to the (encrypted) DB before the slice is used**, so a crash or restart can never reuse an
offset. There is a unit test for the split invariant (`OTPVaultDirectionTest`).

### 3.5 Erase after use (forward secrecy of the keystream)

After a slice is consumed — **on send right after the XOR, and on receive only after the plaintext
is durably saved** (save-then-erase, so a crash can't corrupt a redelivered message) — the consumed
bytes are zeroed by re-sealing just the affected chunk(s) (`OTPGenerator.eraseSlice`,
`OTPVaultManager.eraseRange`). Consumed keystream is therefore unrecoverable even on later device
compromise.

### 3.6 In-memory exposure

Only the chunk(s) a message touches are decrypted into a heap buffer, which is **zeroed immediately**
after the XOR (`SealedPadSlice.use`/`zeroize`). The full pad is decrypted only once, transiently, by
the Bluetooth sender at exchange time (and zeroed right after). (Note: Java/ART can't guarantee zero
residue against a copying GC — see §9.)

### 3.7 Destruction

"Destroy OTP Vault" (`OTPVaultManager.destroySession`) **deletes the Keystore key**, deletes the
`sealed_pads` row, deactivates the session, **and purges that conversation's stored plaintext**.
Deleting the non-extractable Keystore key makes every historical OTP message permanently
undecryptable — forward secrecy on demand.

## 4. Message encryption flow

```
SEND (HybridEncryptionEngine.encrypt, off the main thread)
  plaintext
   ├─ if an active OTP session exists for the peer:
   │     offset = OTPVaultManager.reserveBytes(session, len)     ← atomic, persisted
   │     otpCiphertext = plaintext XOR pad[offset .. offset+len] ← decrypts only needed chunk(s)
   │     eraseRange(offset, len)                                 ← scrub consumed keystream
   │     mode = HYBRID_OTP
   │  else:
   │     otpCiphertext = plaintext;  mode = AES_ONLY
   └─ ciphertext = HPKE.encryptFor(peerPublicKey, otpCiphertext) ← Tink DHKEM-X25519 + AES-256-GCM
  → WireMessage{ ciphertext, mode, otpSessionId?, otpByteOffset?, senderId, recipientId, … } → relay

RECEIVE (WebSocketMessagingService.handleIncoming)
  HPKE.decrypt(ciphertext)                       ← own Keystore-wrapped private key
   └─ if HYBRID_OTP: assertInboundOffset(); plaintext = otpCiphertext XOR pad[offset…]
  save plaintext to Room  →  THEN eraseRange(offset, len)   ← save-then-erase
```

`messageId` is used as HPKE associated data (binds ciphertext to its id). Duplicate deliveries are
dropped before decrypt (so erase-after-receive is safe).

**Sender authentication.** Every content frame (`msg`/`edit`/`unsend`/`reaction`/`timer`/`receipt`/
`key`/`key_ack`) carries the sender's two public keys and an **Ed25519 signature** over a canonical
transcript of its security-relevant fields (`WireMessage.signingTranscript`). On receipt the client,
**before any side effect**, checks `fingerprint(hpke ‖ sig) == senderId` and verifies the signature
with the bound signing key; anything that fails is dropped. HPKE alone is anonymous (anyone holding
your public key can encrypt *to* you), so this signature is what proves a frame actually came *from*
`senderId` — closing message spoofing, forged edits/unsends, and control-frame forgery, even against
a malicious relay. A frame is also rejected if it claims `AES_ONLY` while an OTP pad is active for
that peer (anti-downgrade).

**Live UI updates.** The open chat does not rely on the Room `Flow` alone — Room's invalidation
doesn't reliably fire for these cross-write inserts under SQLCipher, so the service also **pushes**
each received message on a `SharedFlow` (`WebSocketMessagingService.incoming`) that `ChatViewModel`
collects and merges (deduped by id). Your own sent messages are echoed optimistically. Room stays the
durable store (history on open / restart).

## 5. Bluetooth pad exchange (in person)

Uses Google **Nearby Connections** (`P2P_POINT_TO_POINT`), behind a mockable `NearbyTransport`
seam; wire frames are encoded/parsed by a pure, bounds-checked `FrameCodec`. Orchestrated by
`BluetoothKeyExchange`.

```
A (advertiser)                                   B (responder)
── Phase 1: proximity + MITM check ─────────────────────────────────────────
  Nearby connects (authenticated+encrypted channel).
  Both display PIN = SHA-256(SAS token) % 10⁶.  USER verifies the PINs match.

── Phase 2: ephemeral ECDH, bound to the verified channel ───────────────────
  Each generates an ephemeral X25519 keypair; they exchange public keys (FRAME_DH_PK).
  sessionKey = HKDF-SHA256( X25519(myPriv, theirPub),
                            salt = verified SAS token,           ← binds to the PIN
                            info = "OTPPhone-BT-PadKey" ‖ sorted(pubA,pubB) )  ← binds the transcript
  → an active MITM that can't reproduce the PIN can't derive sessionKey.

── Phase 3: pad transfer ────────────────────────────────────────────────────
  A: generate pad → AES-256-GCM(sessionKey) the raw bytes → send metadata + blob.
  B: decrypt → re-seal locally (chunked, under B's Keystore key) → provision session → ACK.
  Both zero the session key and ephemeral private key afterward.
```

The pad bytes are protected by this independent AES-256-GCM layer on top of Nearby's own transport
encryption, and never touch the internet. Sessions are keyed to the peer's stable `userId`, with a
fresh `sessionId` (UUID) per exchange. Bluetooth/Nearby permissions are requested at runtime
(`KeyExchangeScreen` gate); the flow requires two **physical** devices (emulators have no Nearby radio).

## 6. Relay server

`server/Server.kt` — a single-file Ktor WebSocket relay. **It only ever sees HPKE ciphertext and
metadata; it cannot read message content.**

- **Endpoint:** `wss://<host>/ws?userId=<fingerprint>`; `GET /` is a health check.
- **Connect-time authentication:** the client must prove it owns the keys behind its `userId`. The
  server checks `userId == fingerprint(hpkeKey ‖ signingKey)`, HPKE-seals a random nonce to the HPKE
  key (with a domain-separated context info, so the client can never be used as a decryption oracle
  for real message ciphertext), and requires the client to echo the decrypted value. This blocks
  impersonation, key-substitution MITM, and targeted DoS-by-eviction.
- **Forwarding:** reads `recipientId` and forwards the frame, but **only after binding the frame's
  `senderId` to the authenticated connection** (a mismatch is dropped, so no client can forge frames
  from another `userId`) and **refusing to relay reserved handshake types** (`auth_*`/`challenge`/
  `hb_ack`), so one client can't drive another's auth state machine. If the recipient is offline,
  queues up to 100 messages and flushes on reconnect. End-to-end authenticity does not rest on this
  (the per-message signature does, §4); it is defence in depth against a *connected peer* and removes
  a cheap targeted-DoS vector.
- **Protections:** 500-connection cap; sliding-window rate limit (50 msg / 10 s / user);
  stale-session eviction; quiet logging (framework noise suppressed via `logback.xml`).
- **State is in memory** → the relay is **single-instance by design**. It must run as exactly **one**
  machine; multiple machines would be independent relays that can't see each other's connections.

## 7. Hosting & distribution

**Relay (Fly.io).** Packaged as a fat jar (`./gradlew :server:shadowJar` → `server-all.jar`), run in
a JRE-17 container (`server/Dockerfile`), deployed via `fly deploy` using `server/fly.toml`. Fly
provides automatic TLS and the `*.fly.dev` hostname → `wss://otpphone-relay.fly.dev/ws`.
**Scaled to a single machine** (`fly scale count 1`) per §6; `auto_stop_machines = "off"` keeps it
always-on so WebSockets aren't dropped.

**App config.** `BuildConfig.SERVER_URL` is injected per build type (`app/build.gradle.kts`):
debug and release both point at the Fly `wss://…/ws` URL. The network-security config forbids
cleartext (TLS only); `wss://` passes.

**APK distribution (Cloudflare).** The APK is stored in **R2** (object storage, free egress) and a
**Worker** (`distribution/download-worker.js`) serves a download page + streams the APK with the
Android package MIME type, behind `download.rhydianwilliams.com`. The page shows the version and
SHA-256 for integrity.

## 9. Security properties & limitations (read this)

**Provides**
- **End-to-end confidentiality:** the relay only sees HPKE ciphertext; it cannot read messages.
- **End-to-end authenticity & integrity:** every content frame is Ed25519-signed by the sender and
  verified (against the signing key bound into `senderId`) before any side effect, so neither the
  relay nor another user can forge a message or tamper with one (edit/unsend/reaction/timer/receipt
  are all signed too). The relay additionally binds `senderId` to the authenticated connection.
- **Key-substitution MITM resistance:** identities are key fingerprints over *both* keys; peer keys
  are pinned; the relay authenticates by proof-of-possession.
- **No keystream reuse:** direction-split + atomic, persisted offsets + per-message erase.
- **Pad confidentiality at rest:** chunked AES-256-GCM under a non-extractable Keystore key, inside
  a SQLCipher-encrypted DB, in the app sandbox, no cloud backup.
- **Forward secrecy on demand:** destroying the vault deletes the Keystore key and stored plaintext.

**Limitations (honest)**
- **Not a true one-time pad.** The pad is CSPRNG output, so security is *computational* (≈ a stream
  cipher / AES-CTR), not information-theoretic. Do not market it as "unbreakable."
- **Metadata is visible to the relay operator:** who talks to whom, when, sizes, IPs. Content is not.
- **Relay is single-instance / in-memory:** no HA; a restart drops live connections (clients
  auto-reconnect) and queued offline messages. Multi-machine would need shared state (e.g. Redis).
- **Memory scrubbing is best-effort:** `fill(0)` can't defeat a copying GC, and `String` plaintext
  is immutable — so transient plaintext/pad residue may persist in the heap until GC.
- **Bluetooth MITM defence rests on the user comparing the PIN.** The ECDH binding makes a silent
  active MITM fail, but a user who blindly accepts a mismatched PIN defeats it.
- **Distribution build:** the download page currently serves a *debug* APK (debuggable, debug-signed).
  A signed *release* build is the proper distributable (see "remaining work").

**Threat model in one line:** protects message *content* against the network, the relay operator,
and (for OTP messages) future transport-key compromise; does **not** hide metadata from the relay,
and assumes the user's device and the in-person PIN check are trustworthy.

## 10. Remaining work / known gaps

- Replace the distributed debug APK with a **signed release** build (`signingConfigs` not yet added).
- True one-time-pad mode would require a hardware TRNG and immediate full-erase, not a CSPRNG.
- Production hardening: per-IP rate limiting at the edge; optional reduction of relay metadata logging.
- `fallbackToDestructiveMigration()` is still enabled — replace with real Room migrations before a
  stable release (a schema change currently wipes the local DB).
- Sending is gated until the peer's HPKE key is held (no plaintext-first message). Messaging a peer
  who has never been online waits until the exchange can complete; an offline send-queue that holds
  the plaintext locally and encrypts-and-sends on key arrival (no plaintext on the wire) is designed
  but not yet built.
- The relay connection is held only while the app is open (no background service). FCM or a
  foreground service would enable delivery while backgrounded; multi-pad per peer would add OTP capacity.
